## Goals

### Requirement analysis

| Requirement | Observable acceptance | Stages |
| --- | --- | --- |
| Portable remote entry | Main-fiber right-sidebar `git.remote`; GitHub first, with a provider-neutral model rather than GitHub-bound UI; old hosts still load and run local Git | S1, S3, S6, S7 |
| PR workflows | List, detail, file comparison, PR comments, inline comments and approve/comment/request-changes reviews, checkout, create, close, merge | S3–S6 |
| Limited Issue scope | Read-only list, detail, comments; create `issue-{n}-{slug}` through existing branch operations | S3, S4, S6 |
| Identity and permission safety | All-or-nothing credentials seam; writable storage is neither authentication nor repository/action permission; every write binds a repository, stable viewer, and one credential snapshot | S1–S3, S5 |
| Honest failures and concurrency | Persist refresh send intent and never replay possibly consumed refresh credentials; verify checkout SHA, protect concurrent tracking updates, report partial effects; do not misreport unknown remote writes | S2, S4, S5 |
| Lifecycle and budgets | Stop admission, cancel/await owned work on unload; isolate account caches, back off rate limits, deduplicate notifications; Desktop is removable enhancement only | S2, S3, S6, S7 |
| Subsequent GitLab support (In progress) | Stage authentication, MR/Issue, checkout and guarded writes for GitLab.com and self-hosted GitLab (Self-Managed); unsupported actions remain disabled and real-platform acceptance remains outstanding | GL0–GL5 |

Acceptance must extend beyond happy paths: prove no token reaches RPC, logs, or argv; enforce separate API/browser allowlists; prevent workspace/account/generation changes from causing cross-account writes or stale UI.

## Non-goals

- No Review Mode, editor embedding, or GHES. GitLab.com and self-hosted GitLab are outside the initial S0–S7 scope; its subsequent extension follows the separate GL0–GL5 review and implementation gates.
- No Issue mutations, custom queries, hover cards, completion, TODO→issue, or local application of suggestions.
- Create PR accepts already-pushed remote branches, including forks. It does not push or create forks; direct users to the existing push RPC.
- Do not take over Git transport authentication or bridge OAuth tokens into `git fetch/push`; no automatic branch deletion or promise of atomic rollback across refs/config.
- Implementation never touches real credentials, real OAuth, remote writes, or destructive actions; dependency installation/network access needs prior approval, and no commits, pushes, or publication happen without instruction.

## Design

### Boundaries and implementation locations (Planned)

Extend the [current architecture](../../architecture/overview.md): Host owns capability gating, credential runtime, REST providers, Git integration, and `/git` RPC. Client receives only wire-safe state/results; its main fiber owns all portable UI. Git continues through `ctx.subprocess` with separate argv values, without shell, Electron, or Desktop runtime dependencies. Optional Desktop notifications belong in a child `ctx.inject(['desktop'], ...)` fiber declaring only consumed structural methods.

Implement alongside existing Host entry/service, shared types, `src/compat/`, Client controller/sidebar, and their tests. Keep remote state machines and provider modules separate from local Git paths. Establish `docs/reference/remote-platform-rpc.md` as the canonical stable RPC reference when contracts land; architecture links to it rather than duplicating schemas.

- [x] Validate GrantRecord v1, record key/ref, and host/client/app binding. Landed in `src/remote/grant.ts` (`parseGrantRecord` and the state union, `dsh-plugin-git/github-com`) and `auth.ts` (`authBase` mints a `uuid` revision per commit, sha256 in-process digest).

Run `gh` serially only for identity-establishment events: seam mount, credential events, explicit retry, and rebuilding identity after 401; at most one round per event. A 401 becomes invalid with repair guidance, not silent account fallback; anonymous applies only when no credentials ever existed. `establish()`/`resolveContext()` check grant→refs→cached `ghToken`→anonymous in order; `markInvalid` records the fingerprint to block the same token; malformed/unsupported records report `invalid` without falling back to discovery.
- [x] Allow `git credential fill` only as an explicit user action. Credential probes set `GIT_ASKPASS=''`, `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never`, `GCM_INTERACTIVE=never`, and `-c credential.interactive=never`, with ≤5s hard timeout, bounded output, redacted errors, no stdout/stderr forwarding, and no token in argv. - [x] Device Flow uses public client_id from `Config.remote.clientId` and `repo` scope. Persist authorizing/attemptId by CAS first, then commit only the matching attempt. Handle interval, slow_down, expiry, denial, cancellation, and repeated-login exclusion. Hide login without client_id but retain discovery; expiring credentials without refresh tokens become reauth-required. Landed in `startLogin`/`pollLogin`/`cancelLogin`; without `clientId`, `startLogin` rejects and `capability().loginAvailable === false`.
- [x] Sign-out persists signed-out and suppresses discovery across restart. “Clear local authorization” separately calls `deleteRecord` to resume discovery and explicitly does not revoke the token server-side. Landed in `signOut()` (CAS write of signed-out) and `clearLocalGrant()` (`deleteRecord`).
- [x] Refresh prepare must **commit** refreshing/refreshId/basedOnRevision before the owner sends outside the lock. Complete writes new tokens only on matching refreshId+basedOnRevision CAS. Onlookers wait a bounded interval, then require reauthentication; they never resend. Landed in `refresh()`: a lost marker CAS moves to a bounded `waitRefresh` (`refreshPollMs`/`refreshTtlMs`/`refreshExpiresAt`) and adopts the settled result; a failed prepare commit throws before any send.
- [x] Never replay after sent-request timeout, response loss, any 5xx including 502/504, deterministic rejection, complete-commit failure, crash, or restart. A crash after marker commit but before send also burns the attempt. Only transport-confirmed **not sent** permits safe retry; failed prepare commit sends nothing. Failed completion discards new tokens and reports remote-updated/local-uncommitted. Only `GitRemoteTransportNotSent`/`kind: 'not-sent'` takes the restore path permitting a later safe retry; other failures CAS to `reauth-required`; a complete-commit exception/CAS miss throws `{ stage: 'complete', remoteUpdated: true, localCommitted: false }` and keeps the marker.

### Primary structure: unified interface, platform adapters, and instance contexts (Target)

**Origin and status**: On 2026-10-27 the user proposed and designated this as the **primary candidate for technical review**: business services call a unified interface API, with platform implementations encapsulating actual operations. GL0 review/final freezing adopts interface + composition, with ADR-0005 Accepted; this is not implementation authorization.

```text
Remote business service / runtime
  └─ Unified RemoteProvider operation interface
       ├─ GitHubProvider ─ GitHub instance configuration + separate auth context
       └─ GitLabProvider ─ GitLab.com / self-hosted configuration + separate auth per instance
```

This is a candidate target structure. Following the user’s 2026-10-27 scope adjustment, GitLab.com and self-hosted GitLab (Self-Managed) both enter this round’s GL0–GL5 candidate delivery scope, sharing a platform adapter with isolated instance contexts. Design review has passed; implementation has not started.

| Layer / component | Candidate responsibilities and dependency boundaries |
| --- | --- |
| Business service / runtime | Depend on the unified operation interface; orchestrate session/repository assertions, cancellation and local Git workflows. Do not construct platform implementations directly or build platform REST paths. Existing Git integration still executes Git through `ctx.subprocess` with separate argv |
| Unified interface and neutral models | Define reads, writes, results, errors and per-operation capabilities; distinguish unsupported actions from unknown permissions without erasing PR/MR, approval or discussion differences |
| Platform adapters | `GitHubProvider` / `GitLabProvider` encapsulate API paths, parameters, responses and semantic mappings. Python abstract-base/subclass design is an analogy; this round chooses TypeScript interface + composition, considering a base class only for verified shared workflows |
| Instance configuration and auth context | Separate platform type from origin. GitLab.com and self-hosted GitLab normally reuse the GitLab adapter, with API/web origins, App and capabilities supplied by instance configuration. Isolate grants, viewers, generations, caches and in-flight work per instance; validate origins explicitly rather than allowing arbitrary RPC input to become an authentication target |
| Factory / registry and shared mechanisms | At the assembly boundary, select and inject an interface implementation for a validated repository/instance; business services do not maintain platform branches. Prefer composition for HTTP, credential storage, cancellation and budgets. Consider an abstract base only for verified common workflows, avoiding accumulated platform conditionals |

**Difference from today and review alternatives**: `RemoteProvider` exists, but runtime directly holds `GitHubProvider`, and repository types, auth and HTTP remain GitHub-specific. The primary candidate completes dependency inversion and separates platforms from instances. GL0 compares it with adding platform branches in the business layer and concentrating shared workflows in an inheritance hierarchy, assessing compatibility costs, isolation, testability and capability differences before freezing a choice. Do not create a subclass per origin; evaluate specialized adapters only for actual protocol/behavior differences.

### Self-hosted GitLab included in this round (Proposed)

Self-hosted instances move from structural preparation into this round’s candidate delivery scope under these concrete review boundaries. Configurable origins alone do not constitute accepted self-hosted support.

| Included item | Design and acceptance requirements |
| --- | --- |
| Instance URLs and deployment prefixes | Explicit HTTPS bases, non-default ports and optional deployment prefixes; private-network domains/IPs may be user-configured targets, never automatically trusted from remotes/responses. Normalize scheme/host/default ports/trailing slashes while preserving path case; reject userinfo, queries/fragments, path escapes and ambiguous encodings. Prefix routing covers API/OAuth/web links. The official [relative-URL deployment guide](https://docs.gitlab.com/omnibus/settings/configuration/#configure-a-relative-url-for-gitlab) labels that mode Beta, requiring separate verification evidence |
| Identity and credential addressing | Instance identity distinguishes scheme, host, effective port and deployment prefix. Freeze credentials-key-compatible host-id encoding and collision handling. Same-host instances with different ports/prefixes and identical user/project/object ids must not share grants/caches. URL changes never migrate tokens automatically; instance edits/removal cancel old requests and invalidate confirmations/cursors |
| Instance authentication | Use each instance’s App/client_id and scopes; verify registration prerequisites against [official App configuration](https://docs.gitlab.com/integration/oauth_provider/). Never assume the GitLab.com App applies. Review actual Device Flow availability and credentials-seam refs for existing tokens when App/flow support is absent; no fallback to other-host environment/CLI identities or tokens/secrets in settings |
| Network and trust | Send credentials only to the registered instance’s API/OAuth boundaries; independently validate redirects, Links, web/avatar URLs by purpose. Pages/repository input cannot expand trust. HTTPS certificates must be trusted by the Host runtime; verify enterprise-CA configuration and proxy compatibility in GL0 without disabling TLS verification or adding Desktop dependencies. Plain HTTP and ignored certificate failures remain out of scope |
| Git remote mapping | Model HTTPS API/web bases separately from Git SSH endpoints (host, port, repository path). Standard HTTPS/SSH remotes match explicit instances; SSH aliases or different reverse-proxy endpoints require explicit mappings with unique ownership, never inferred new API origins.
