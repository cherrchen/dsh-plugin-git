# Remote-platform RPC contract (remote-*)

- **Status**: Current implementation, covered by mocks and temporary repositories; real OAuth, remote writes and platform manual acceptance remain Not verified.
- **Authority**: [ADR-0004 Decision](../decisions/ADR-0004-remote-platform-integration.md#decision) (Proposed) and the [implementation plan](../plans/active/remote-platform-integration.en.md).

## Gate and lifecycle

The `/git` channel disables the entire feature without a complete credentials seam. Structural checks require readRecord, modifyRecord, deleteRecord, resolve, describe, describeRecord and notifyRecordUpdated, including inherited methods; event emitters are never called by the probe. Missing names come from an allowlist; provider/getter/process/network diagnostics and secrets never propagate.

A credentials child fiber owns authentication, REST, caches and subprocess work. Unload stops admission, cancels and drains work, preserving the local Git service and Changes/Diff/Graph/Worktrees. The Client main fiber polls capability every five seconds and registers/removes `git.remote` type/body/title. Session/workspace changes cancel old requests; account/generation changes discard stale data. Desktop notification, authorization browser and user-code copy enhancements live in an optional child fiber.

The seam uses local structural types without production or published-declaration imports of the optional package; older hosts can build and load without it. Release lanes are governed by the [compatibility contract](dsh-compatibility.md).

## remote-capability

Without a remoteProtocol marker the payload remains ignored, including null. Missing seam returns `{state:'off',reason:'credentials-missing',auth:{state:'off'}}`; incomplete seams return credentials-incomplete and missing names. implementation-pending remains a fail-closed fallback when the runtime has not assembled.

With a complete seam the unscoped result preserves `{state:'on',generation,credential,auth,actions,loginAvailable,automaticRefreshAvailable,authSelection?}` and adds the `remoteProtocol:2` advertisement. Capability launches no subprocess or network activity; it reads storage descriptions and known in-memory authentication state. Storage configured/writable does not prove authentication or remote permissions. Initial auth is unauthenticated and actions are unknown. Repository viewer, permissions and actions are returned separately by remote-repository.

`generation={instanceId,revision}` is opaque to clients; runtime replacement never reuses instanceId. Viewer identity is stable host/userId; login is presentation only. GET /user runs at most once per generation. Explicit retry creates a fresh generation; rejected tokens do not silently fall back to another account.

## Scoped v2 foundation (Current)

With a complete seam, unscoped capability advertises `remoteProtocol:2`; the Client sends v2 only after seeing it. Marked requests must use `2`; except cross-instance `remote-repositories` and orphan retirement they carry `{provider,instance}`. Success returns `{remoteProtocol:2,scope,generation,value}`; capability generations match inside and outside, and void uses `value:null`. Seam off and RPC errors are control results with no trusted generation. The Client checks marker, canonical scope and generation, discards stale/out-of-order replies and never downgrades a failed v2 write to an unscoped write. GitHub scope is `https://github.com`; v1 fields, grant and unscoped calls keep their meanings.

v2 `remote-repositories` accepts `repository/sessionId?` and returns `{remoteProtocol:2,value:{state,remotes,unresolved?}}`; every recognized identity carries scope. It reads only local origin/upstream, explicitly registered instances and built-in GitLab.com. Unknown domains are not probed or echoed; ambiguous SSH mappings return a sanitized `ambiguous` reason. A missing seam remains global off.

Unscoped v2 `remote-accounts` accepts only `{remoteProtocol:2}` (any extra key rejects as invalid-request) and needs no session or repository; it returns `{remoteProtocol:2,value:{accounts}}` listing the fixed GitHub entry plus every registered GitLab instance's `{provider,instance,label?}`, never clientId, credentialRef, sshHost or secrets. Scoped v2 `remote-account` requires the scope but no repository: it establishes identity non-interactively with the same discovery rules as a first read and returns that scope's `ScopedRemoteCapabilityOn` including `viewer` when authenticated. GitHub reads the viewer through the legacy owner's per-generation shared cache — at most one GET /user per generation — and sends no network request when unauthenticated. The plugin settings page lists these accounts under "Platform accounts" and opens the same authentication dialog as the Remote page.

GitLab scoped capability, `remote-login`, `remote-poll-login`, `remote-cancel-login`, `remote-sign-out`, `remote-clear-grant`, `remote-retry-auth`, repository-level `remote-repository`, MR/Issue lists and details, commits, notes, discussions, current approval facts, file comparisons, MR checkout, Issue branching and guarded MR comment/approval/create/close/direct-merge Host endpoints are wired. Repository facts accept the local repository, full `path`, optional `projectId` and object `{kind,number}`; the Host first matches the instance and path against local origin/upstream, then verifies the API's `path_with_namespace` and id. Before each page and before responding it rechecks the local remote and session, and it checks authentication generation before responding. `actionScope` identifies the repository or object; `operationSupport`, method/event sets, actions and `reviewPermissions` separately report implementation/policy and permission facts. Unknown permission does not mean denied; unconfirmed project features or methods are not enabled. Unimplemented remote writes still reject `git/remote-unavailable`, without fabricated success. Project identity reads are not cached; authenticated object reads are cached by instance, viewer, generation, project and full request path, and conditional requests require an ETag. Anonymous reads are manual only, and authenticated automatic reads wait at least 60 seconds and honor rate limits. Instance capability actions remain false; `authMethods.deviceFlow` starts unknown and explicit attempts can establish supported/unsupported. Capability reads storage descriptions and in-memory state only: no network or subprocess. Explicit `remote-retry-auth` validates identity and may read instance metadata; a returned `serverVersion` is marked `support:'unknown',reason:'not-verified'`, not a server compatibility claim. Missing metadata does not switch a validated identity; authentication 401 still marks it invalid.

Each GitLab instance owns grant v2, App, viewer, random generation, requests and login attempts. Discovery order, ref binding/failure classification, URL rules and the 838-character maximum are in [design D2/D4](../architecture/remote-platform-instances.en.md). Device Flow uses the instance App and `api` scope; bearer tokens go only to `<prefix>/api/v4/`, while OAuth and browser verification paths are separately constrained without REST bearer. Missing `expires_in` prevents token commit. Automatic refresh requires a refresh token and a deployment’s positive `refreshStoreExclusive` guarantee for the **actual store**. Persistent intent/CAS prevents replay after unknown outcomes; a missing replacement refresh token never reuses the old one. Project lookup permits only the exact encoded path generated from an authorized local remote; other API paths continue to reject percent encoding and redirects are bound to the original request. List continuation uses a Host-managed random handle bound to instance, project, viewer, generation, query and session. A request reads at most 10 pages and continues via a handle; missing pagination headers cause an error rather than a completeness claim. Pagination Link route echoes `id`, `noteable_id` and `merge_request_iid` are checked against the current project/object path. Only verified defaults for that endpoint are admitted; unknown or duplicate additions and query changes fail. The continuation is constructed from the original Host query and validated page number, without forwarding server-added parameters. First/last/prev links are scope-checked too, and next must advance exactly one page. MR/Issue projections distinguish global id from project-local iid; MRs preserve source/target projects, branches and supplied SHAs, project `locked` as `open` while retaining the raw value, and keep unknown states read-only. Registry updates validate the full configuration: invalid updates retain the previous valid snapshot; an invalid initial configuration retains built-in GitLab.com and GitHub discovery, and retirement rejects while configuration is invalid; changed/removed contexts cancel and drain. Volatile Host references have no subscription API, so the Host reconciles every second and rechecks critical authentication steps and scoped responses.

GitLab `remote-comments` and `remote-discussions` require `objectKind:'pull'|'issue'` and project-local `number`. The former returns read-only individual notes; discussion members the notes API also echoes (DiffNote/DiscussionNote and resolvable notes) are excluded. The latter returns genuine discussions only — the `individual_note` wrappers GitLab adds for every plain note are excluded so the same note is not rendered both as a comment and as a thread — with independent discussion ids, notes, available resolved/resolvable values and diff positions including both paths/lines, base/start/head and line ranges. Thread ids are never review ids. `remote-approvals` returns current fields and approvers actually supplied by the API, without fabricating review history. `remote-files` rechecks the MR comparison snapshot for the first and subsequent pages; continuations carry `expectedBaseSha`, `expectedStartSha` and `expectedHeadSha`, and the cursor binds all three. A changed snapshot returns `git/head-moved`; collapsed, too-large, empty and missing patches have explicit states. Upstream diff limits may omit files independently of pagination, so `serverCompleteness:'unknown'` always states this limitation; `files.truncated:false` only means no further page link and does not prove the server supplied every change. GitLab `remote-reviews` and inline comment submission remain unavailable.

GitLab `remote-checkout-pr` and `remote-issue-branch` require canonical `expectedInstance`, `expectedGeneration`, stable `expectedViewer` and `requestId`. The Host re-resolves the project and object and rechecks session, remote and the credential snapshot before local side effects. Checkout fetches only the target project's `refs/merge-requests/<iid>/head` through the matching origin/upstream into a private ref isolated by instance and target project id, then verifies the API head SHA. Same-project branches track the source; forks default to `mr-<iid>` and an existing default name requires a different name. Receipts report known private-ref, tracking, fetch-mapping, switch, upstream and actual-HEAD states; an observed branch in another worktree adds `worktreeConflict:true`. Branches are not automatically rolled back or deleted. Issue branches are created and switched from a checked local HEAD, with created or unknown steps reported on failure. Process-local requestId deduplication returns the same result for the same content and rejects different content; Git transport uses existing Git credentials, never platform tokens.

GitLab remote mutators require the same identity/session confirmation; comment, review, close and merge explicitly carry `objectKind:'pull'`. `COMMENT` sends a normal note; `APPROVE` includes the expected head SHA. APPROVE remains disabled when reauthentication is required or the policy cannot be confirmed, and no password is collected. Approval with a body checks support first, then sends comment → approve. A known second-step failure returns partial; an unknown sent approval returns `git/write-result-unknown` with the successful comment id in details, and the same requestId never resends it. Direct merge offers only the `merge` or `squash` choice supported by both project policy and the object's current `squash_on_merge`; a missing or conflicting object fact disables it. The Host rereads the facts before writing and explicitly sends the selected squash value, expected SHA and `should_remove_source_branch:false`. Project or branch policy can still change after that check; there is no atomic policy precondition. If a receipt confirms the merge but omits or contradicts the squash result, or reports source-branch removal, the Host returns partial with the known merge fact and requires inspection without retrying. Draft, locked, unknown or known-blocked objects are rejected. Close, create and comment lack an atomic SHA precondition; their pre-send checks are best-effort. Create `head` must carry same-instance `provider`, `instance`, `path` and validated `projectId`; both source and target must be local origin/upstream and the Host verifies both remote branches without pushing or creating a fork. Branch encoding is limited to a GET bound to the exact numeric project and branch. Post-send timeout, lost response or 5xx, context invalidation after a completed write, and a Client receipt whose scope/generation cannot be verified all require `git/write-result-unknown` reconciliation against the affected object; confirmed-not-sent, permission denial and partial completion are distinct. GitLab inline writes, Issue writes, REQUEST_CHANGES, unapprove, rebase and auto-merge still reject.

The portable Client main fiber offers GitHub/GitLab switching, instance/repository selection from local remotes, per-instance authentication repair, MR/Issue browsing, current approvals, discussions, commits and comparisons. Object facts gate supported actions. An old Host that does not advertise v2 receives no GitLab scoped requests. Close and merge show instance, repository, object, head SHA and account before a second confirmation, which context changes invalidate. Partial or unknown outcomes block repeat submission until the affected object and relevant pages are refreshed and explicitly inspected; local Git partial receipts also require inspecting the branch and worktree. Submission deduplication and reconciliation state last only for the current process. GitLab bodies use a safe Markdown subset, show unknown HTML as text, restrict links to the validated instance, display image alt text without automatic image loads, and support safe disclosures; inline writes remain disabled.

Remote loading and platform authentication reuse the discovered remote provider; detailed behavior is specified in [Client loading feedback](#client-loading-feedback-current).

GitLab `remote-notifications` reads only pending, structured `action_name:review_requested` MR todos for an authenticated viewer and a validated project. It independently verifies project id/path, target project/id/iid, state and safe web links. Continuations reuse opaque cursors bound to instance, project, viewer, generation, query and session. It never marks todos done or infers changes-requested from natural language or approval snapshots. The Client deduplicates by instance, project, account, generation, object and state/time, and rechecks only the current user’s previously loaded MRs. Post-push suggestions apply only to a verified local origin/upstream: explicit push uses origin; sync projects the optional `pushedRemote` only when machine-readable Git push destination and branch match before and after the push. Ambiguous destinations are not guessed. Notices remain in their GitLab view; native notification is an unloadable enhancement. This limited coverage and failed requests do not represent all account events.

`remote-retire-grant` accepts only `{remoteProtocol:2,provider:'gitlab',instance}`; the Host fully normalizes input and derives its own key. An unregistered scope may be cleaned using storage only; registered scopes reject. Under the lock, it verifies the v2 binding and replaces secrets with a new-revision retired signed-out marker. The receipt `{remoteProtocol:2,scope,generation:null,value:{disposition}}` uses `retired`, `already-retired` or `absent`. No enumeration, network, external ref resolution or server-token revocation occurs. Ordinary `remote-clear-grant` still deletes the active local grant and resumes discovery. The plugin settings "Platform accounts" section offers a two-step cleanup entry below the account card: enter the old instance URL, review the canonical scope and confirm deletion.

GitHub scoped reads/writes use an explicit adapter over the existing owner. Writes additionally require `expectedInstance:'https://github.com'` and deduplicate by scope, repository, generation, viewer and requestId plus a content fingerprint. v2 repository/object facts separately expose operationSupport and supported method/event sets. Merge methods derive from the repository’s `allow_merge_commit` / `allow_squash_merge`, remain disabled without evidence, and are rechecked before writing. Remote Issue writes are unsupported and their actions are false. v2 write receipts include outcome/steps, with partial outcomes for checkout and issue-branch. Existing GitHub v1 behavior does not depend on v2.

## Configuration and authentication

Configuration parsing/validation lives in src/remote/settings.ts and its schema in src/index.ts. All fields are optional volatile values:

| Field | Default | Meaning |
| --- | --- | --- |
| clientId | release default or absent | GitHub public Device Flow client ID; explicit configuration overrides the release default and an empty string disables it; no effective ID disables OAuth with a hint while retaining discovery |
| instances | built-in GitLab.com | Up to 16 explicit GitLab entries with `url`, `label?`, `clientId?`, `credentialRef?`, `sshHost?`, `sshPort?`; identity rules are in [instance design D2](../architecture/remote-platform-instances.en.md#d2-configuration-and-instance-identity-gl-r2-gl-r9-gl-r13) |
| requestTimeoutMs | 15000 | Total HTTP deadline, including redirects and body reading |
| probeTimeoutMs | 5000 | Non-interactive probe deadline, 1–5000 ms |
| refreshTtlMs | 30000 | Persistent refresh intent and observer wait TTL |
| refreshPollMs | 250 | Positive observer interval, no greater than TTL |
| refreshStoreExclusive | false | Deployment attestation of cross-process modifyRecord exclusion; otherwise no automatic rotation |
| maxResponseBytes | 4194304 | Per-response byte cap; cancel oversized streams immediately |

The sole registry of release application IDs is root [`oauth-apps.json`](../../oauth-apps.json), containing the maintainer-supplied public GitHub.com OAuth App and GitLab.com public OAuth Application IDs. Normal `pnpm build`/`pnpm bundle` embeds them into the Host artifact; the Client continues to initiate login through RPC without embedded secrets. Build environment variables `DSH_GIT_GITHUB_CLIENT_ID` / `DSH_GIT_GITLAB_CLIENT_ID` override registered values, with an explicit empty variable disabling that platform build default. Runtime `remote.clientId` / GitLab.com instance `clientId` takes precedence over embedded defaults; an explicit empty string disables the default. Self-managed instances never inherit the GitLab.com app. Source/test modules without injected build defaults still need explicit application configuration. No runtime environment read or client secret is added. Effective App changes retain existing grant binding/invalidation rules. Registered and bundled IDs do not prove successful real device authorization or account login.

Login results retain `expiresAt`/`intervalMs` and GitLab may add optional `verificationUriComplete`; the Client accepts older results without these optional fields and omits the countdown when expiry is absent. The public data never includes `device_code` or tokens.

GrantRecord v1 uses key dsh-plugin-git/github-com. Transitions use modifyRecord CAS and a fresh revision. Discovery is authenticated grant → GH_TOKEN/GITHUB_TOKEN refs → gh auth token → anonymous. Ref source is provider-defined and resolved per operation; gh runs only for identity establishment/events/explicit retry, never per REST page. A rejected token becomes invalid without switching identity; loss of a previously present credential never silently becomes anonymous. Git credential fill is explicit, non-interactive and receives fixed host/protocol over stdin. Probe output never enters RPC, logs or argv; probes have bounded collection, ≤5s deadlines and exit drain.

The optional negotiation field `authSelection?:{method:'auto'|'cli'|'oauth',cliAvailable:boolean,oauthCached:boolean}` reports known in-memory facts only: capability polling never reads secrets, starts CLI or sends network requests. Identity establishment reads the persisted preference; missing preference means `auto`, preserving the discovery chain above. Selection uses a separate standard credentials `kind:'grant'` metadata record at `dsh-plugin-git-auth/<original grant host-id>` with payload `{v:1,provider,instance,method,revision}`, containing no token. Preferences are instance-bound; unknown fields or invalid bindings fail closed without silently changing accounts. CLI credentials stay under gh/glab management and are never copied into OAuth grants; the existing glab discovery entry point supports GitLab.com only.

Selecting CLI persists the preference and establishes CLI identity without deleting the OAuth grant. Selecting OAuth first reuses the instance-bound grant, applying existing expiry, App binding, 401 and refresh exclusivity/CAS checks; Device Flow starts only when reauthorization is needed. Credentials persist both records across Host recreation; expired, revoked or App-mismatched tokens never become valid just because they are cached. `oauthCached` indicates known local data available for cleanup, not token validity. “Log out of OAuth” cancels local login attempts, removes access/refresh tokens and persists a secret-free signed-out marker. It never invokes gh/glab logout, deletes CLI credentials or revokes server tokens. Explicitly selected CLI identity remains active; otherwise OAuth identity and implicit discovery stop until explicit CLI selection or OAuth login. Legacy `remote-sign-out` / `remote-clear-grant` retain their global suppression/discovery semantics and reset selection to auto.

| Authentication endpoint | Payload / result |
| --- | --- |
| remote-login | {} → attemptId,userCode,verificationUri,expiresAt,intervalMs; no device_code/token on wire |
| remote-poll-login | attemptId → authenticated; shares one poll per attempt, accumulates slow_down, rejects denied/expired/cancelled authorization |
| remote-cancel-login | attemptId; cancel polling and CAS-finish that attempt |
| remote-select-auth | `{method:'cli'|'oauth'}` → capability; persist selection without deleting the OAuth grant |
| remote-oauth-logout | `{}` → capability; remove only OAuth secrets and retain a signed-out marker |
| remote-sign-out | {}; persist signed-out to suppress discovery |
| remote-clear-grant | {}; delete only the local grant, resume discovery, no GitHub server revocation |
| remote-retry-auth | {}; explicitly rebuild identity, return capability |
| remote-use-git-credential | {}; explicit non-interactive helper probe, return capability |

Device Flow verification is restricted to https://github.com/login/device. Refresh first CAS-commits an intent marker, exchanges outside the lock, then commits new tokens only for matching refreshId/basedOnRevision. Failed prepare sends nothing. Only confirmed-not-sent permits restoring the old snapshot. Timeout, cancellation, 5xx, response loss or crash never replay the exchange and converge to reauth-required. Failed completion discards new tokens and reports complete/remoteUpdated/localCommitted facts.

## Repository reads

remote-repositories accepts repository/sessionId? and returns `{state:'supported'|'no-remotes'|'unsupported',remotes:[{name,identity}]}`. Only supported GitHub HTTPS/SSH origin/upstream identities enter the allowlist; URL credentials and other hosts are rejected.

Other repository endpoints carry repository/sessionId?/host:'github.com'/owner/repo. The Host verifies local remote membership. Reads return `{generation,value}`; lists use `{items,truncated,next?}`: `truncated` reports that upstream still has more beyond the fetched pages, and `next` is an opaque continuation cursor (the upstream `Link rel="next"`, origin-checked against the API allowlist and free of credentials). List endpoints additionally accept `{cursor?,pages?}`: `cursor` resumes from a previous `next` (the provider re-validates its origin and rejects foreign origins), `pages` bounds how many upstream pages one request may read (default 1, clamped to the per-request page cap). Each page holds at most 100 items (notifications 50) and a single request reads at most the page cap, but there is no total-item ceiling — the Client streams pages with the cursor until exhaustion; cache size is capped at 128 entries.

| Endpoint | Additional fields / value |
| --- | --- |
| remote-repository | Viewer, known original permission bits, five tri-state actions; storage writability proves no remote permission |
| remote-list-prs / remote-list-issues | state?:open/closed/all, cursor?, pages?; Issue lists exclude PR entries |
| remote-pr / remote-issue | number; explicit PR head/base repository/ref/SHA, open/closed/merged plus rawState; `createdAt` keeps upstream `created_at` |
| remote-comments | number,inline?, cursor?, pages?; replyTo, commitSha, original line/side, outdated state and `reviewId` (owning review id for nested display); `createdAt` keeps upstream `created_at` |
| remote-commits | number, cursor?, pages?; `{items,truncated,next?}` of `{sha,subject,author,date?,committedAt?,url?}`, `committedAt` from `commit.committer.date` |
| remote-reviews | number, cursor?, pages?; `{items,truncated,next?}` of `{id,author,state,rawState,body,url?,submittedAt?,commitSha?}` with `state` normalized to `approved/changes-requested/commented/dismissed/pending` |
| remote-files | number, cursor?, pages?, expectedBaseSha?, expectedHeadSha?; files:{items,truncated,next?},baseSha,headSha; verify PR snapshot before/after the first page, then pin head/base on each continuation. PR detail no longer calls it proactively: file changes open the GitHub Files page via `pr.url + '/files'`; the capability remains for guarded write paths that need local coordinates |
| remote-notifications | automatic?; review requests and own PR merged/closed/changes-requested events with stable ids; expand at most ten threads, explicitly mark truncation |

Tokens go only to https://api.github.com with X-GitHub-Api-Version:2022-11-28. Pagination Link and GET redirects obey the same allowlist; browser links independently require https://github.com, and avatar URLs (the viewer and every `author.avatarUrl`) further require credential-free `https://avatars.githubusercontent.com` or are omitted. Explicit projections prevent raw response leakage. Successful `GET /user` results are reused within a generation; a failed lookup clears the cached viewer promise so later operations can query again, subject to authentication and rate-limit gates. Authenticated ETag/body caches are isolated by origin/viewer/generation/full path and query, and cleared when identity changes. Anonymous reads are manual only. Authenticated polling waits at least 60s and honors stricter X-Poll-Interval. Rate limits honor Retry-After/reset and bounded exponential backoff. Writes never retry automatically.

### Client loading feedback (Current)

`github-markdown.ts` normalizes the HTML subset in remote bodies into Markdown and disclosure blocks. Numeric entities are converted only within `0..0x10FFFF`; out-of-range entities retain their original text so malformed PR/Issue bodies or comments cannot interrupt detail rendering.

The Remote list, detail view and authentication dialog show a status banner distinguishing remote discovery, connection to the identified platform, list/discussion reads, authentication connection, waiting for user authorization and action submission. Network waits longer than eight seconds show a slow-response hint; waiting for Device Flow user authorization is not treated as a slow network. The initial list uses skeleton rows without prematurely reporting missing remotes or an empty filter result. Lists and detail collections request only one page initially, then fill the rest through the existing cursor stream with background-loading feedback. Refreshing or changing filters preserves existing rows and their original PR/Issue kind so their details remain accessible; writes retain busy/unknown guards. Failed requests clear loading feedback, surface a toast with a short localized summary that hides the raw code — the code and allowlisted details fields are reachable only through the toast's copy-details action — and restore the explicit refresh control; content surfaces no longer render red error text and show only a muted tertiary line on first-load failures. All copy is bilingual and animations respect reduced-motion preferences.

The authentication dialog is titled "{platform} account" and stacks an identity card (avatar, `@login`, connection state or login feedback) above two described method cards (CLI and OAuth, each with one availability/description line). GitLab dialogs append GitLab-only notes (the sign-in covers GitLab content only; notification coverage); GitHub dialogs never show them. Headlines, sources and authorization text follow the provider; unknown sources omit the source label. Checked state derives only from capability, and CLI authentication never hides OAuth. OAuth requires `loginAvailable`, writable storage and Device Flow support. Missing App, read-only or unsupported methods remain disabled with reasons; unknown support permits an explicit attempt with a hint. Hosts advertising `authSelection` use `remote-select-auth`, show saved OAuth status and offer “Log out of OAuth” only for local OAuth authorization. Older Hosts without that field retain legacy endpoints (switching to CLI may clear the old grant). The device-login card expands in place beneath the OAuth option; orphan GitLab grant cleanup now lives in the plugin settings "Platform accounts" section, still requiring canonical-URL review and separate confirmation.

GitLab rate-limit/backoff and server polling intervals are isolated by credential digest within each instance; reads, approval-policy checks and writes share that credential's budget. CLI/OAuth switching cannot carry one credential's `blockedUntil` into another. Returning to the original credential or only recreating its authentication generation preserves its cooldown. Budgets live only for the Host instance lifetime; map keys are digests, never raw tokens or RPC fields. Response/pagination/cursor caches retain their existing generation isolation. If the new credential also receives a server rate limit, honor its own Retry-After/reset and backoff; never replay writes automatically.

After GitLab reads return `git/signed-out` or `git/unauthenticated`, revoke repository/viewer/action facts and cancel old requests, then read the same instance's authentication capability on the new request lane. Confirmed signed-out is a normal status rather than a persistent raw error code; known signed-out skips protected repository/list reads. If capability discovery temporarily fails, opening the dialog or explicitly authenticating can retry that instance's capability. Never use global GitHub capability to decide GitLab login availability. Recovery neither clears the signed-out marker nor logs in automatically; only explicit CLI/OAuth selection resumes authentication.

Selecting OAuth makes the Host request a code automatically. The controller retains the attempt, uses existing polling and automatically opens the browser once per attempt. GitLab prefers `verificationUriComplete` after Host/Client checks of origin, deployment prefix, exact path and one query matching the current user code; older Hosts fall back to the plain link. GitHub uses only its documented plain verification page, with Copy device code for the user to paste and confirm. Copy failure never reports success. Opening failure, absent Desktop or enhancement unload preserves the manual link and selectable code. Structural `shell.openExternal` and `clipboard.writeText` callbacks belong only to the unloadable Desktop child fiber. HTTP/polling stays in the Host, while the browser opens on the current Client device, including with a remote Host.

While waiting, method changes are disabled and a countdown uses server expiry. Browser opening is not authorization success; completion revalidates the account and refreshes the correct instance. Cancellation, expiry, denial and network failure show localized outcomes and permit explicit retry without automatically creating another attempt. Closing the dialog retains the attempt for reopening. Instance/workspace/account changes, unload and explicit cancellation discard late replies and clean up the owned attempt. Authentication immediately refreshes capability and follows an older in-flight read with another read. Tokens, fingerprints and `device_code` never enter the UI; the displayed/copied value is `userCode`. See [browser E2E](../development/browser-e2e.en.md) for isolated validation boundaries.

### Client caching and incremental validation (Current)

`GitRemoteFeature` owns controllers per session and view, separating the list from individual PR/Issue details. Unmounting a tab retains its state and in-flight pagination; unloading the feature cancels all work. Caches live only in the current Client memory, never on disk, and are cold after restart. New views evict idle controllers in least-recently-used order once 64 slots are occupied. Mounted controllers, active pagination/retries and unknown write outcomes are protected, so protected entries can temporarily exceed 64. Each controller also retains up to 12 list snapshots keyed by remote identity, pulls/issues and open/closed/all filters. Returning within the same workspace restores the selected filter, loaded pages and details.

Returning to a view or filter reuses data younger than 60 seconds; stale data stays visible during validation. Switching remote identities first clears the previous target's rows, detail collections and cursors. The old target's content stays hidden even if the new load fails or pagination is incomplete; returning to the original target can still restore its separate cache. Explicit refresh and detail `navigation.revision` changes bypass the relevant freshness gate. Five-second capability polling alone does not revalidate lists or introduce anonymous automatic network polling. Validation failures for the same target retain content and errors without render-driven retry loops; explicit refresh remains available.

Refresh validates pages from the beginning using the Host's existing ETag / `If-None-Match` support: unchanged pages reuse their bodies on 304, and only changed pages transfer new bodies. This is conditional updating per page, rather than item-level delta synchronization through an upstream change cursor. The Client merges by stable id and retains unchanged row references. Old tail pages remain visible while validation continues; the final page removes records absent from the new result, covering closures, deletions and changes in ordering or page boundaries.

Workspace rebinding, capability off and identity/generation changes clear view/filter caches and cancel old requests. Remote writes, including failures and unknown outcomes, invalidate sibling caches for the same local repository. Tab switches, cache hits and automatic validation never clear an unknown-write gate: explicit targeted refresh is still required, and writes are never replayed automatically.

Controller notification polling pauses while Device Flow authorization is pending, preventing new requests on the same scoped lane from invalidating the in-flight login response. Successful authorization refreshes authentication and the list. Switching methods or logging out of OAuth during an in-flight GitLab operation cancels old work while retaining its original target scope for the authentication request; late replies cannot overwrite the new state.

## Guarded writes

Every repository mutator is enumerated in isRepositoryWrite. In addition to repository identity, payloads require expectedGeneration, expectedViewer:{host,userId}, and requestId. Submission ids contain 8–200 alphanumeric/hyphen characters. A repeated process-local submission returns its original result, including unknown outcomes; retain at most 512 submissions and refuse further admission rather than evicting and replaying effects. Host checks local session directory, remote identity, stable viewer and the same token snapshot at admission and before sending; final resolution compares identity without replacing the checked sending token.

src/remote/diff.ts derives anchors from original hunk headers and validates them on the Host: file/commit/side/hunk plus ordered multiline ranges. Payloads use line/side, start_line/start_side and commit_id, never deprecated position. The current portable UI renders no local diff and has no anchor picker, so `remote-inline-comment` stays unexposed; inline review comments are read-only and nested under their review via `reviewId`.

Checkout fetches a private ref keyed by base repository hash and verifies API head SHA. Tracking updates use expected-old CAS, zero SHA for absence, head-moved for an advanced ref and refusal for divergence. Missing fetch mappings are appended. Branches start at the verified SHA; existing SHA/upstream must match. User branches and other worktrees are never forced. Receipts report switched/privateRefWritten/trackingRefPrepared/fetchMappingAdded/upstreamNotConfigured/branch, actual head when readable, and error. False means completion was not confirmed, not a promise of cross-ref/config rollback. Prepared state is not automatically deleted. Git transport uses existing Git credentials, without OAuth bridging.

Sent-request response loss/timeout/cancellation/5xx yield git/write-result-unknown. Client retains the warning and disables further writes until explicit targeted refresh and inspection. No automatic resend occurs. Successful responses project only id/number/url/merged. Permission/scope/SSO errors and moved heads require repair or renewed confirmation.

## Errors and evidence

Codes: git/remote-unavailable, git/unauthenticated, git/signed-out, git/insufficient-scope, git/head-moved, git/rate-limited with resetAt, git/write-result-unknown, git/remote-identity-mismatch. Without the seam all other known/unknown remote endpoints fail closed before payload parsing.

Automated evidence lives in tests/remote-*.spec.ts and tests/remote-surface.client.spec.tsx. The [plan log](../plans/active/remote-platform-integration.en.md#progress-and-validation-log) records real OAuth/SSO, remote-write, platform-manual and full-release-matrix status. Mocks and the development pin cannot substitute for those checks.

Authentication switches, retries, and completed OAuth login from a GitLab detail view reload the original MR/Issue and its object permissions under the new identity, preserving the navigation target; logout withdraws the previous identity’s data.

v2 scoped mutations, like the legacy channel, invalidate all session, list-filter, and detail caches for the same local repository on success, rejection, or response loss; targeted reconciliation gates for unknown outcomes remain in place.

When a running GitHub Host observes a changed authentication preference revision in shared credential storage, it withdraws the old identity and establishes the selected CLI identity on the next snapshot. Even an absent candidate is probed once; ordinary reads do not repeatedly launch the CLI.
